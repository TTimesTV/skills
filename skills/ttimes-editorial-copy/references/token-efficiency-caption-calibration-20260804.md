# 토큰 효율화 인터뷰 자막 캘리브레이션 — 2026-08-04

## 목적

코딩 에이전트·토큰 프루닝·프롬프트 캐시·스마트 라우팅 발화를 TTimes 화면 문구로 압축할 때 적용한다. 아래 문구는 이번 세션에서 PD가 승인하거나 직접 교정한 표현이다.

## 용어

```text
프롬프트 캐싱(Prompt Caching) : 반복해서 사용하는 지시문·문서 등의 처리 결과를 저장해 다시 계산하지 않고 비용과 응답 시간을 줄이는 기술
```

```text
캐시 라이트(Cache Write) : 반복 사용할 프롬프트를 처음 처리해 캐시에 저장하는 과정
```

- `프롬프트 캐시 재사용`을 쓴다.
- `캐싱 재활용`, `프롬프트 캐시 재활용`은 피한다. 캐싱은 전체 과정이고, 저장된 캐시는 `재사용(reuse)`하는 것이 정확하다.
- `Grep(그렙)`이 정확한 표기다. 여러 파일에서 단어나 코드 패턴의 일치 위치를 찾는 검색 도구다. 실제 파일 내용 읽기는 `Read`와 구분한다.
- `Rounds`는 에이전트가 한 과제를 해결하며 반복한 `판단 → 도구 호출 → 결과 확인 → 다음 행동` 단계의 평균 횟수다.

## 구조자막

```text
1) 프롬프트 캐시 재사용
2) 도구 출력 토큰 프루닝
3) 도구 호출 경로의 결정론적 설계
4) 스마트 라우팅
```

스마트 라우터 구현 방식을 세 부류로 나눌 때는 중간 설명을 되살리지 말고 아래처럼 병렬 명사형으로 정리한다.

```text
1) 경량 LLM 기반 라우팅
2) BERT 분류기 기반 라우팅
3) 정규식·룰 기반 라우팅
```

- `BERT`는 발화에서 분류기 모델로 명시된 경우에만 쓴다.
- 실제 서비스는 세 방식을 섞을 수 있지만, 원 발화가 `세 종류`를 설명하는 구조자막이라면 먼저 세 축만 보여주고 하이브리드·폴백 설명은 별도 비트로 분리한다.

## 강조자막

도구 출력 경량화:

```text
도구를 반복 호출할수록
반환값 경량화가 토큰 비용을 좌우
```

결정론적 경로:

```text
도구 선택지는 줄이고 실행 경로는 고정
에이전트의 시행착오와 토큰 낭비 절감
```

스마트 라우팅 비용 효과:

```text
품질 저하는 미미하지만
비용은 90% 이상 절감
```

`비용이 1/10~1/15 수준`이라는 원 발언을 화면 문구로 바꿀 때는 `십분의 일`, `1/10`을 그대로 옮기기보다 `90% 이상 절감`처럼 효과를 바로 읽히게 쓴다. 단, 원 발언이 **기존 비용의 1/10~1/15로 감소**한다는 뜻이고 수치 근거가 확인된 경우에만 사용한다.

## 질문자막

두 가능성을 화자가 예시로 들었더라도 답을 양자택일로 떠먹이지 않는다. 최종 질문이 정체·방식·구조를 묻는다면 열린 질문으로 쓴다.

사내 사례·경험을 묻는 질문은 원문의 **경험 축**을 보존한다. `겪어봤나`, `필요성을 체감했나`를 임의로 `어떻게 적용·구현하고 있나`로 바꾸면 게스트에게 다른 답을 요구하게 된다. 특히 회사명이 명시됐으면 주어를 유지하고, 구현 질문으로 넓히지 않는다.

거절 후 여러 후보를 요청받으면 실제 질문축을 달리한다: `직접 경험 / 비용 문제 / 성능 유지 / 내부 적용 / 필요성 체감`. 같은 문장의 표면어만 바꾼 후보를 나열하지 않는다.

승인 방향:

```text
스마트 라우터는 어떤 방식으로 제공되나?
```

피할 표현:

```text
스마트 라우터는 모델사가 제공하나
별도 서비스를 이용해야 하나?
```

## 팩트 주의

- `품질 2% 증가`는 `%`와 `%p`를 구분한다.
- 프루닝 논문의 일부 표본에서 `62% → 64%`라면 `2% 증가`가 아니라 `2%p 상승`이다.
- `214줄 → 14줄`은 원 논문에서 확인되기 전까지 자막 확정 수치로 사용하지 않는다.
- SWE-Pruner 검증 수치와 실험 범위는 아래 감사 메모를 확인한다.

## SWE-Pruner 주장 감사

### 원출처

- 논문: **SWE-Pruner: Self-Adaptive Context Pruning for Coding Agents**
- arXiv: `2601.16746`
- 최초 공개: 2026-01-23, 갱신: 2026-05-07
- 원문: https://arxiv.org/abs/2601.16746
- 코드: https://github.com/Ayanami1314/swe-pruner

권장 출처 표기:

```text
출처: Yuhang Wang 외, 「SWE-Pruner: Self-Adaptive Context Pruning for Coding Agents」, arXiv:2601.16746 (2026)
```

### 전체 SWE-Bench Verified 500개 결과

- Claude Sonnet 4.5 기반 Mini SWE Agent: 성공률 `70.6% → 72.0%`(**+1.4%p**), 토큰 `0.911M → 0.701M`(**23.1% 감소**), 평균 라운드 `51.0 → 41.7`.
- GLM 4.6 기반 Mini SWE Agent: 성공률 `55.4% → 56.6%`(**+1.2%p**), 토큰 `0.791M → 0.488M`(**38.3% 감소**), 평균 라운드 `49.3 → 36.6`.

출판 안전 문구:

```text
SWE-Bench Verified 실험에서
토큰 사용량 23~38% 감소
성공률 1.2~1.4%p 상승
```

### `2% 향상` 범위

별도의 무작위 **50개 표본** 비교에서 기본 Mini SWE Agent는 성공률 `62%`, 토큰 `0.972M`; SWE-Pruner는 성공률 `64%`, 토큰 `0.670M`이었다. 따라서 `2% 향상`이 아니라 `성공률 +2%p`, 토큰은 `약 31% 감소`라고 쓴다. 전체 500개 결과로 일반화하지 않는다.

### 미확인·범위 교정

- `214줄 → 14줄`은 논문 본문·부록·공개 저장소·저자 기술 설명에서 확인되지 않아 **UNVERIFIED**다. 확인되는 유사 수치는 LongCodeQA의 최대 `14.84배 압축`이다. 원 슬라이드·페이지가 나오기 전에는 화면 숫자로 쓰지 않는다.
- 실험 프레임워크는 Mini SWE Agent·OpenHands이고 기반 모델이 Claude Sonnet 4.5·GLM 4.6이다. `Claude Code 자체 실험`이라고 쓰지 않는다.
- `Grep`은 관련 코드 위치 검색, `Read`는 파일 내용 읽기다. 두 기능을 한 도구로 합쳐 설명하지 않는다.
