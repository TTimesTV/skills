# AI 영상 카메라 연출과 현실성

사용자의 우선순위는 카메라 구도·무빙과 현실성이다. 대사·음악·립싱크는 요청하지 않으면 추가하지 않는다. 한국어로 설계를 설명하고, 실행 프롬프트 언어는 사용자 요청을 따른다. 상세한 설명을 원하면 생략하지 않는다.

## 사용자 지정: 이미지 콘티 승인 후 영상 생성

2026-10-08 사용자 요청에 따라, 영상 제작은 **번호 붙인 이미지 콘티 제작 → 사용자 검토·수정 → 명시적 승인 → 승인된 콘티로 영상 생성** 순서로 진행한다.

- 계획만 설명하고 승인을 요청하지 않는다. 먼저 실제 콘티 이미지를 제작·확인해 사용자에게 보여준다. 이미지 제작 시 imagegen 스킬과 도구를 사용한다.
- 사용자 선호는 **만화 형태의 4컷을 한 장에 담은 콘티**다. 복잡한 이동이면 6컷·8컷 등 짝수로 늘린다. `01.`, `02.`처럼 번호를 붙이고 카메라 위치·이동 방향·시선·연결 움직임을 짧게 표시한다. 타이밍이 정해졌다면 예상 시간을 덧붙인다.
- 검토용 번호·설명과 이동 화살표는 한 장의 콘티 보드에 표시한다. 구도 승인 후 실제 생성 모드에 필요한 개별 키프레임을 글자 없는 PNG/JPG로 준비한다. 만화 콘티를 실사 영상의 시작/끝 프레임으로 그대로 넣지 않는다. 사용자가 요구하지 않은 개별 이미지 생성을 승인 전에 필수로 늘리지 않는다.
- 구도, 건물 면, 공간 관계와 프레임 간 연결 가능성을 먼저 자체 검토한다. 생성 이미지의 실제 지리 정확성은 별도 검증하며, 확인하지 못한 부분을 명시한다.
- 구체적인 콘티를 보여준 뒤 “이 콘티로 영상 생성에 들어가도 될까?”라고 승인받는다. 이는 사용자가 직접 정한 제작 절차다. 응답이 없거나 수정 요청만 있으면 영상 생성을 시작하지 않는다.
- 승인된 버전과 컷 번호를 기록한다. 승인 범위 안의 작업에는 반복 확인하지 않는다. 승인된 구도·방향·경로를 실질적으로 바꿔야 하면 수정 콘티를 다시 보여주고 승인받는다.
- 프롬프트만 요청하거나 기존 결과를 분석하는 작업에는 불필요한 승인을 요구하지 않는다. 사용자가 해당 작업에서 콘티 단계를 생략하라고 명시하면 그 지시를 따른다.

## 작업 순서

1. **목표와 실패를 분리한다.** 새 영상인지, 원본의 특정 구간 수정인지 확인한다. 보존할 구간, 바꿀 구간, 원하는 마지막 화면을 기존 대화에서 먼저 추출한다. 사용자가 이미 정한 조건을 다시 묻지 않는다.
2. **입력 기능을 확인한다.** 서비스명만으로 모델을 추정하지 않는다. 실제 선택한 모델·버전·화면·생성 모드, 길이/해상도, 시작/끝 프레임, 이미지 참조, 모션 참조, 구간 수정 지원과 동시 사용 가능 여부를 확인한다. 파일명은 단서일 뿐 확정 근거가 아니다. 최신 공식 문서와 실제 UI가 다르면 현재 UI를 기준으로 가용성을 적는다. 불명확한 기능은 `unverified`로 표시하고 조건부 프롬프트를 준다.
3. **공간 설계를 먼저 작성한다.** [카메라와 현실성](references/camera-and-realism.md)을 읽는다. 카메라의 위치, 이동 방향, 바라보는 방향, 피사체 방향을 따로 쓴다. 실제 장소는 지도·항공사진·사진의 촬영 방향을 확인하고 근거를 기록한다. 사진처럼 보이는 것과 실제 지리 일치는 별도 판정한다.
4. **참고 자료의 역할을 지정한다.** 각 파일을 시작 프레임 / 끝 프레임 / 외형 참고 / 공간 검증 / 움직임 참고 중 무엇으로 쓸지 명시한다. 반대편에서 찍은 정면 사진을 목표 시점의 끝 프레임으로 쓰지 않는다. 생성 이미지는 확인 전까지 실제 배치의 증거가 아니다.
5. **생성 경로를 선택한다.** [워크플로와 프롬프트](references/workflows-and-prompts.md)를 읽고 지원되는 입력으로 구성한다. 이동 경로와 마지막 장면의 충돌을 글로 덮지 않는다. 이미 좋은 앞부분은 편집에서 보존하고 필요한 뒷부분만 생성하는 방식을 우선 검토한다. 사용자의 생성 요청을 지도 녹화나 실사 촬영으로 임의 대체하지 않는다.
6. **이미지 콘티를 제작하고 승인받는다.** 위 사용자 지정 절차를 적용한다. 승인 전까지 영상 생성은 진행하지 않는다. 승인 후 설계와 실행문을 아래 출력 형식으로 전달한다. 자세한 설계가 필요하다고 해서 모델에 모순되는 지시를 누적하지 않는다. 반대로 무조건 짧게 줄이지도 않는다. 선택한 모델 가이드에 맞게 구체성을 조정한다.
7. **검증하고 한 번에 한 요인을 바꾼다.** 결과를 실제로 열어 확인한 범위만 판정한다. 사용자가 정한 비용·횟수 제한을 따른다. 동일한 공간 오류가 두 번의 통제된 수정에도 유지되면 같은 방식의 재시도를 멈추고 이미지·입력 모드·구간 분할을 재검토한다. 두 번은 이 스킬의 비용 절약 휴리스틱이며 모델의 공식 한계가 아니다.

## 출력 형식

- **원하는 장면:** 도착 화면과 보여야 할 면, 보존할 요소를 먼저 한 문단으로 설명한다.
- **입력 설정:** 서비스/모델/모드, 길이/화면비/해상도, 첨부 파일별 역할과 업로드 슬롯. 없는 입력 슬롯에 `IMAGE1`을 쓰면 제어된다고 말하지 않는다.
- **카메라 설계:** 시작 위치 → 이동 경로 → 시선 → 종료 위치/시선. 초 단위 계획은 연출 목표이며 정확한 타임코드 제어를 보장하지 않는다고 필요한 경우 짧게 밝힌다.
- **복사용 프롬프트:** 사용자가 원하는 상세도로 제공한다. 영어 요청 시 지명은 `Seoul City Hall (서울시청)`처럼 표기할 수 있다. 중요한 공간 관계와 한 가지 주된 움직임을 우선한다.
- **확인 항목:** 해당 샷의 합격 기준 3–5개와 다음 실패 시 바꿀 요인 한 가지를 지정한다.
- **실행 상태:** `pass / fail / skipped / not_run / unverified`를 실제 범위별로 표시한다. 프롬프트 작성 완료와 영상 생성 성공을 혼동하지 않는다.

## 검증 기준

처음·중간·끝과 전환 직전/직후 프레임을 확인하고 전체 재생으로 시간적 연속성을 확인한다. 정지 프레임 검사만 했다면 무빙 판정은 `unverified`다.

- 공간: 도로 연결, 건물 면과 위치, 앞뒤 순서, 가림, 좌우 관계가 참고 근거와 맞는가?
- 카메라: 이동과 회전이 구분되는가? 피사체가 돌아가거나 도시가 재배치되어 카메라 이동을 흉내 내지 않는가?
- 물리/외형: 원근·시차·크기·그림자, 차량 이동, 창문/지붕의 시간적 일관성이 유지되는가?
- 편집: 접합부 구도·속도·고도·색·노출이 이어지는가? 같은 경계 프레임도 속도의 연속성을 보장하지 않는다.
- 요구 충족: 실제 보존 요청 구간이 유지되고 필요한 끝 화면에 도달했는가?

## 근거와 유지관리

사실 확인과 도구 선택에는 [리서치 노트](references/research.md)를 사용한다. 공식 기능, 제작자의 경험, 커뮤니티 일화, 이 스킬의 제안을 구분한다. 모델 기능은 사용 시 재확인한다. 성공률이나 정확한 지리 재현을 보장하지 않는다. 사용자 보고 실패도 실패 사례로 보존하되 직접 검증한 것처럼 쓰지 않는다.
