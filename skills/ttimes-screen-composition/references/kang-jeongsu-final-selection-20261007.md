# 강정수 1·2편: 초안에서 사용자 최종본으로의 판단 보정

2026-10-07 사용자가 비교분석을 화면구성 스킬의 지속 학습 참고로 반영하도록 명시했다. 이 문서는 승인된 **편집 선택의 사례와 적용 기준**이며, 모델 가중치 학습이나 외부 사실 검증을 뜻하지 않는다.

## 근거와 적용 범위

- 프로젝트: `LOCAL_REFERENCE_NOT_DISTRIBUTED`.
- 사용자 최종 JSON: `1편/강정수 뮤즈 1-1_데이터_20261007.json`, `1편/강정수 뮤즈 1-2_데이터_20261007.json`, `2편/강정수 뮤즈 2편_데이터_20261007.json`.
- 상세 보고서: 프로젝트의 `강정수 화면구성 초안과 최종본 비교분석_20261007.docx`.
- 감사 기록: `LOCAL_REFERENCE_NOT_DISTRIBUTED`의 `drafts.json`, `finals.json`, `cases.json`, `all_79_audit.json`, `assets_inventory.json`, `qa.json`.
- 실제 assistant 보관 초안 5개 버전을 구분했다. 최초 통합 79개 제안 전체를 검토하고 공통 발화 42개 사례를 대조했다. 프로젝트 폴더의 후속 수정 Word를 순수 assistant 최초본으로 오인하지 않았다.
- 최종 사용 항목은 1-1 48개, 1-2 48개, 2편 90개로 총 186개다. 이 내보내기에서는 `used`가 선택 집합이었다. 자료·자막·컷·교정·종료 표시가 섞여 있으므로 79 대 186으로 채택률이나 자막 밀도를 계산하지 않는다. 다른 JSON 스키마에 이 상태 규칙을 무조건 적용하지 않는다.
- 1편의 두 파일은 한 편의 분할 자료다. 원고 잔존 구간과 개정 시각이 겹치므로 같은 발화로 연결하며 시각을 단순 이어 붙이지 않는다. 2편도 원고 시각과 개정 영상 시각을 동일시하지 않는다.
- 번호 자료 65개 중 정지 이미지 52개를 확인했고 영상 13개는 각 3개 장면을 추출했다. 완성 영상 전편 시청, 자료 영상 전체 재생, 외부 사실 검증은 하지 않았다. 정확한 문자 앵커가 없는 23개 항목의 세부 IN/OUT은 미확정이다.
- JEV 6회(입력 23,454 / 출력 2,538 토큰) 후 42개 사례를 직접 판정했다. 토큰 절감률은 측정하지 않았다.

## 다음 화면 구성에 적용할 판단

### 1. 개념도를 만들기 전에 실제로 볼 수 있는 것을 찾는다

초안의 Gmail·캘린더·건강 데이터 통합 구조도는 최종본에서 Gmail 연결 캡처 → 건강 정보 연결 캡처 → 뉴스 브리핑 시연으로 구체화됐다. Computer Use도 정의만이 아니라 실제 브라우저와 직접 조작 화면으로 보여줬다.

제품의 동작·개인 체험은 해당 화면이나 결과물을 먼저 검토한다. 식별에는 로고/사진, 주장의 입증에는 해당 부분이 읽히는 원자료, 행동에는 시연, 관계·순서·분모에는 그래픽이 적합한지 비교한다. 실제 화면이 있다는 이유만으로 무조건 넣지 말고 해당 발화에 필요한 역할을 확인한다. 뒤늦게 확보된 자료로 인한 제작 단계의 진전과 취향 차이를 구분한다.

### 2. 체험담의 대화와 반응을 결과 요약으로 지우지 않는다

- 초안: “구독 15개 중 잘 안 보는 4개 정리”.
- 최종: 뮤즈 캐릭터가 비서처럼 해지를 제안하는 말풍선 → “그래서 해지했습니다”라는 반응.
- 보험 사례도 만기·납입·수익·중복 보장에 대한 구체적인 비서의 안내로 풀었다.

체험의 효용뿐 아니라 제안 → 사용자 행동 → 결과/반응의 순간이 있는지 고른다. 대화를 재구성하면 원문에 근거하고 직접 인용과 편집 요약을 구분한다. 캐릭터나 농담은 이 사례의 표현 수단이지 모든 인터뷰의 의무가 아니다. 초안의 다른 농담들은 최종에 없으므로 ‘항상 더 웃기게’로 학습하지 않는다.

### 3. 문장 길이보다 주체·행동·비교축을 구체화한다

| 초안 | 최종 선택 | 적용할 판단 |
|---|---|---|
| 챗GPT 모멘트에 버금갈 큰 변화 | 챗GPT 모먼트에 버금가는 뮤즈 모먼트 | ‘큰 변화’ 대신 대상 명시 |
| 승자가 그대로여도 판은 다시 흔들릴 수 있다 | AI가 쇼핑의 입구가 되면 / 흔들릴 수 있는 네이버·쿠팡의 양강구도 | 원인과 영향받는 주체 명시 |
| 일은 대신 맡겨도 즐기는 건 내가 직접 | 시간을 빼앗는 일은 AI에게 / 시간을 즐기는 일은 사람에게 | 비교의 기준을 같은 문법으로 제시 |
| 가상머신의 기술적 정의 중심 | 서버 안에 마련된 나만의 가상 컴퓨터와 프로그램·파일 설명 | 더 길어도 이해에 필요한 구체적 설명 유지 |

‘서비스 1등 가능’처럼 원문보다 강한 최종 문구는 강도 보정의 자동 정답이 아니다. 가능성·개인 경험·순위·수치의 범위는 따로 검토한다.

### 4. 내용 선정과 함께 화면의 변화 시점을 정한다

- 호텔 예약: 이용자↔OTA↔호텔을 먼저 보여주고 이용자↔AI↔호텔로 전환, 후속 설명에서 같은 기준 화면 재사용.
- 클라우드: SSD 먼저 → ‘연산’에서 GPU/HBM 추가 → ‘실행’에서 CPU 추가 → 개인 가상 컴퓨터 설명까지 유지.
- 아마존: 협력의 득실과 차단의 득실을 발언 순서에 맞춰 제시.
- 고정비: 빈 트럭 비유만 제시하기보다 고정비 10만 원을 100건/90건으로 나눌 때의 단가 차이를 가정과 함께 계산.

첫 등장, 추가/교체, 유지/재사용, 종료가 의미에 영향을 주면 정확한 발화에 연결한다. 처음부터 결론을 모두 보여줘 발언을 앞서가지 않는다. 줄바꿈만으로 순차 등장시키지 않으며 색·좌표·동작을 불필요하게 고정하지 않는다. 식별용 ‘아무 장면’처럼 사용자가 열어둔 편집자 재량은 보존한다.

### 5. 긴 답변의 방향을 질문과 소제목으로 안내한다

초안의 명시적 질문 자막은 1개, 최종은 8개(1편 2개, 2편 6개)였다. 이 숫자는 할당량이 아니다. 메타의 강점, 커머스 영향, 은행·카드, 기기·스마트폰, VM 연산처럼 실제 주제가 전환되는 곳을 안내한다. 답변 안에서는 ‘아마존 위협 요인 ① 쇼핑 시작점 변화 / ② …’처럼 논지를 나눌 수 있다. 모든 인터뷰 질문을 그대로 Q 자막으로 만들지 않는다.

### 6. 확인 메모를 자료 선택과 교정 행동으로 연결한다

WSJ 확인 메모는 읽을 기사 제목으로, 모델 순위는 해당 지수의 점수 막대로, 마이크로소프트 사례는 사용할 영상 구간으로, 아마존 수익성은 해당 사업 부문의 영업이익률 자료로 구체화됐다.

허용된 자료 탐색 범위에서 실제 출처와 볼 부분을 확인하고 선택·교정까지 진행한다. 미해결 ‘확인 필요’를 반복해 완성된 화면 구성처럼 보고하지 않는다. 미확보라면 자료설계 상태와 필요한 다음 행동을 명시한다. 영업이익률·순이익률·매출총이익률, 지역 부문·AWS처럼 지표와 대상이 다른 것을 혼용하지 않는다. 사용자가 승인한 자료도 사실·권리 검증 완료를 뜻하지 않는다.

### 7. 현재 질문과의 관계를 먼저 확인한다

1-2의 “질문이 메타랑 뭐가 다르냐는 건데”라는 명시적 컷 의견은 정보의 흥미보다 현재 질문에 대한 답인지를 우선한 사례다. 주제에서 벗어난 대목에 새 자료를 과도하게 설계하지 않는다. 화면구성만 요청된 작업에서 원문을 임의로 삭제하지 말고 해당 편집 판단을 별도로 표시한다.

원문 자체가 최종 컷에서 제거된 경우와, 원문은 남았는데 제안만 빠진 경우를 구분한다. 후자의 삭제 이유는 명시적 피드백이 없으면 미확정이다.

## 유지할 강점과 잘못 일반화하지 않을 것

- “깜빡한 기차표까지 / 먼저 챙겨주는 비서”, “최고보다 중요한 / 충분히 쓸 만한 서비스”는 유지됐다. Good Enough 비교와 호텔 예약 경로의 기본 구조도 유효했다. 모든 초안을 전면 교체할 필요는 없다.
- 기차표 자막은 선정의 배경 설명 전체보다 결론 절에 앵커를 좁혔다. 선정 이유의 범위와 실제 노출 범위를 나눠 판단한다.
- ‘항상 짧게’, ‘그래픽을 줄여라’, ‘더 단정적으로’, ‘질문 8개’, ‘캐릭터 필수’는 이 비교의 결론이 아니다.
- 폴더에 파일이 있다는 것만으로 최종 사용을 확정하지 않는다. 1편 26번 그래픽은 파일이 있지만 최종 JSON의 명시적 호출/배치는 확인되지 않았다.
- 공통 의미가 남았다고 assistant 제안이 원인이라고 단정하지 않는다. 최종 문구의 오타나 검증되지 않은 사실은 선호로 학습하지 않는다.

## 계속 쌓아갈 때의 기록 방식

새 비교를 사용자가 요청하거나 실제 수정 피드백을 주면 기존 분석을 덮어쓰지 말고 필요한 사례만 추가한다. 자동 감시·예약 작업·외부 업로드를 의미하지 않는다.

각 사례에는 **원본 버전/근거 → 공통 발화 → assistant 제안 → 사용자 승인 선택 → 차이와 근거 수준 → 적용 조건/반례**를 남긴다. 구체적인 제작 상황에 묶인 선택은 사례로 유지한다. 반복된 선택이나 명시적 사용자 지시에서만 일반 기준을 좁게 갱신하고, 후속 반례가 나오면 이전 해석을 수정한다.

비교는 사용자의 확정 문구·의도, JSON 지시, 실제 구현 관찰을 구분한다. JEV에는 같은 발화의 짝과 앞뒤 맥락 및 필요한 기준만 전달하고, 반환 분류를 직접 검토한다. 의미 기능의 변경과 문구 유지/수정을 별도로 판단해 모든 변경을 ‘자료 교체’ 하나로 뭉개지 않는다.
